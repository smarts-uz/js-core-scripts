## What This Project Is

A collection of **Node.js (ESM) tools for processing Office and Markdown documents** on Windows. Every operation is a **public static method of a class under [`classes/`](classes/)**, exposed as a CLI through a **per-method runner** at `scripts/<Class>/<method>.mjs`. Runners are launched directly with `node`, from Windows right-click context menus via the `sheller/` launchers, or from VS Code debug configs. There is **no server, UI, or build step**. The project carries a `package.json` (jest test scripts + dev tooling only) and a `jest` unit-test suite under `tests/`.

Operation families (each a method on a `classes/` class, runnable via `scripts/<Class>/<method>.mjs`):

- **Conversion** — Word→Markdown and Markdown→DOCX/HTML: `Word.wordToMD`, `Markdown.convertToWord`, `Markdown.convertToWordTOC`, `Markdown.convertToHtml`.
- **Homoglyph normalization** — Latin→Cyrillic look-alike replacement across four formats: `Homoglyph.{word,excel,powerpoint,markdown}` plus their interactive `*Ask` variants.
- **Excel operations** — `Excels.*`: change font, recalc, replace (Formula/Formula2/FormulaArray/Standard/All), protect/unprotect (file & sheet), hide/unhide, merge.
- **Word / PowerPoint** — `Word.*` / `PowerPoints.*`: protect/unprotect, merge files / merge folders.
- **Merge & misc** — `Markdown.merge`, `Excels.{mergeFiles,mergeFolder}`, `PowerPoints.{merge,mergeFolder}`, `Word.{merge,mergeFolder}`, `Yamls.mergeYamlsInFolder`, `Chromes.{saveHtmlFromMht,convertFolderMhtToHtm,processPathsToClipboard}`, `Scanner.run`, `Category.{run,revert}`, `Registry.clean`.

### Runtime & module system — concrete values

Owned by `smarts-app-cmd` → `module/runner-tree.md`, `module/dependencies.md`. This project's fill-ins:

- **Node.js ESM**. Runners are `.mjs` under `scripts/<Class>/`; `classes/` and the rest are `.js` with `"type": "module"`. A runner runs directly: `node scripts/Word/wordToMD.mjs --file <file>`.
- **CLI parser = `yargs`** (`hideBin(process.argv)`), one `.option()` per method parameter, inside each standalone `scripts/<Class>/<method>.mjs` runner generated by `scripts/_generate.mjs`. Primary file flag `--file`/`-f`; array params take positional arrays (`a.docx b.docx …`); object params take `--key value`.
- **No `node_modules/` at this project root — never symlinked, never real, since 2026-08-16.** The prior real-Windows-directory-symlink convention (`node_modules` → `C:\Users\Administrator\.node\node_modules`) is retired machine-wide (`smarts-install-js`'s case-3 convention now uses exactly two wiring mechanisms — `NODE_PATH` for CommonJS, `package.json` `#imports` subpath for ESM — see `smarts-install-js` → `module/dependencies.md`). This project is `"type": "module"`, so it uses the `#imports` mechanism: a small per-package **bridge file** lives in `import/` at the project root (a direct sibling of `classes/`/`scripts/`/`package.json`) for every third-party package `classes/`/`scripts/` imports — each bridge file re-exports the real shared-store module via a `file://` absolute URL (`export * from 'file:///C:/Users/Administrator/.node/node_modules/<pkg>/<entry>';` plus a separate `export { default } from '...'` line, since `export *` alone does not forward a `default` export). The project's own root `package.json` carries an `"imports"` map (`{"#pkgname": "./import/pkgname.mjs", ...}`) — every source file imports via the `#`-prefixed specifier (`import yaml from '#js-yaml'`), never the bare package name and never an inline `file://` path. `package.json`/`package-lock.json` are no longer symlinks either — this project's own real `package.json` carries no `dependencies`/`devDependencies` blocks (per the shared-store convention), only the `imports` map, `scripts`, `name`, `engines`, module type. Node's `imports` field rejects an absolute external filesystem path as its target (verified live: both a plain Windows path and a `file://` URL throw `ERR_INVALID_PACKAGE_TARGET`) — this is *why* the bridge-file indirection exists, not an implementation detail to skip. A NEW package added for this project still installs into the shared store first (`smarts-install-js action=install scope=global "<pkg>"`), then gets its own bridge file + `#imports` entry added here — never a local `npm install`. Run the jest suite with `NODE_OPTIONS=--experimental-vm-modules` set (via `cross-env`, per the npm `test` script) — invoking `jest-runtime`'s bin directly without that flag fails every suite with `Cannot use import statement outside a module`; that failure is an invocation mistake, not a module-resolution problem.
- **The `dependencies`/`devDependencies` blocks live ONLY at `C:\Users\Administrator\.node\package.json`** (the shared store's own real content — every runtime package `classes/`/`scripts/` imports, `winax`, `yargs`, `puppeteer`, `js-yaml`, `turndown`, `xlsx`, `pino`, `dotenv`, etc., plus the vendored global CLI tools, see below). This project's own root `package.json` is a real, local (never symlinked) file carrying `name`/`type`/`engines`/`scripts`/`lint-staged`/the `imports` map — never a `dependencies`/`devDependencies` block. Before trusting a package is available, cross-check `C:\Users\Administrator\.node\node_modules\<pkg>` actually exists for anything `classes/`/`scripts/` imports AND that project's own `import/<pkg>.mjs` bridge file + `package.json` `imports` entry exist — a whole-file rewrite has previously dropped the entire real `dependencies` block by accident (see the CLI-tools note below).
- **Global CLI tools are ALSO vendored as regular `dependencies`** (`@anthropic-ai/claude-code`, `@openai/codex`, `@google/gemini-cli`, `vercel`, `supabase`, `npm`, `pnpm`, `yarn`, `bun`, `corepack`, `skills`, and others) — added deliberately so `npm install` places their binaries in `node_modules/.bin` instead of relying on a global install that gets wiped whenever the active Node version is switched (via `fnm`). **When adding a new package to `dependencies`, always keep the real runtime deps too** — a whole-file rewrite of `package.json` (e.g. a large scaffolding commit adding CI/lint/husky config) has previously dropped the entire real `dependencies` block by accident, silently breaking every `scripts/` runner (`ERR_MODULE_NOT_FOUND` for `winax`, then `yargs`) until a later session diffed `package.json` against git history and restored it.

### The homoglyph utility (centralized) — project-specific

- All homoglyph scripts delegate to a single `classes/Homoglyph.js` — **one `PERFECT_STEALTH` Latin→Cyrillic look-alike map** (21 pairs: `A→А a→а C→С c→с E→Е e→е H→Н I→І i→і J→Ј K→К M→М O→О o→о P→Р p→р S→Ѕ T→Т X→Х x→х y→у`) shared across Word/Excel/PowerPoint/Markdown.
- Public API per format: `Homoglyph.{markdown,word,excel,powerpoint}(file, chars)` and the `*Ask(file)` interactive variants. Plain variant takes optional `--chars`/`-c` (subset; omit = all); `-ask` variant prompts via `Dialogs.inputBox()`, filters to known mappings, and persists to `ChoosedChars.*`.
- Format application: Markdown = read→regex→write; Word = COM `Find.Execute` with `MatchCase=true`; Excel = COM cell iteration honoring `ExcludedSheets`; PowerPoint = COM slide/shape iteration. Each copies the source first, then edits the copy.

### Excel replace — distinct COM strategies (project-specific)

- **`Excels.replaceFormula` / `replaceFormula2` / `replaceFormulaArray` / `replaceStandart`** — winax COM; each uses a different cell API (Formula vs Formula2 vs FormulaArray vs value); enumerate via `SpecialCells(-4123)`.
- **`Excels.replaceFormulaAll`** — winax COM; enumerates via `UsedRange.SpecialCells(23)` + `Areas` (robust for non-contiguous ranges).
- **All Excel work uses `winax` COM (`Excels` helper) — there is no pure-JS / SheetJS path.**

### Merge — files vs folders (project-specific)

All three COM classes expose a parallel `merge` (explicit files, array param `$files`) + `mergeFolder` (one folder per arg, each contributing its **latest file by mtime**, skipping `~$*` temp files) pair:

- **`Word.merge`** — merges given `.docx`, starting from the latest template in `Templates.WordMerge`, inserting page breaks and updating all TOCs. **`Word.mergeFolder`** — latest `.docx` per folder, no template.
- **`Excels.mergeFiles`** — copies every sheet of each source workbook into a fresh workbook, suffixing sheet-name collisions (`_1`, `_2`, …, ≤31 chars). **`Excels.mergeFolder`** — latest `.xlsx` per folder, delegates to `mergeFiles`.
- **`PowerPoints.merge`** — appends every slide of each source onto a copy of the first file via COM `Slides.InsertFromFile`. **`PowerPoints.mergeFolder`** — latest `.pptx` per folder, delegates to `merge`.
- Output naming is uniform: beside the first file, named after that folder (or an explicit `mergedName`), auto-incremented via `Files.incrementFileName`.

### COM robustness — concrete per-class

Owned by `smarts-app-cmd` → `module/classes.md` (safe-open-with-repair, orphaned-process cleanup, `null` not `undefined` for skipped COM args). This project's concrete implementations:

- **Safe-open:** `Excels.openWorkbookSafely` uses `CorruptLoad` (1 = `xlRepairFile`, 2 = `xlExtractData`); `Word._safeOpen` (via `Com.openWord`) retries `Documents.Open(..., OpenAndRepair=true)`, then a plain read-only open when repair also fails (both a plain and a repair open need an exclusive lock, which fails identically when the file is already open in another Word session — a read-only open only needs a shared lock, so it succeeds regardless); `PowerPoints._safeOpen` falls back to read-only (PowerPoint has no `CorruptLoad`).
- **Orphan kill — shared `Com.pidsOf`/`Com.killOrphans` (`classes/Com.js`), used by EVERY COM-driving method in `Word.js` AND `Excels.js` (15 methods each), never a bespoke single-PID kill.** Snapshot the target image's PIDs (`Com.pidsOf('WINWORD.EXE'|'EXCEL.EXE'|'POWERPNT.EXE')`, `tasklist /FO CSV` via `execSync`) as `before`, right after `checkWinax(...)`/right before `new winax.Object(...)`; then in `finally` (after `Quit()`/`winax.release()`, each independently try/caught so one failing step never skips the next) call `Com.killOrphans(imageName, before)`, which diffs the _current_ running PIDs against `before` and `process.kill`s only the PID(s) this run itself spawned — a user's own already-open Word/Excel is never touched. **`Excels.generate()` additionally wraps its whole COM-driving body (`processAccrual`/`processPayment`/`processLoaners`/`processPenalty`/the `{KEY}` replace loop) in `try/finally`, calling `fileClose()` in `finally`** — before this, a mid-loop exception (e.g. the 255-char `replaceInSheet` crash below) skipped `fileClose()` entirely, leaving `EXCEL.EXE` orphaned with a lock on the just-created output file (confirmed live: the very next `generate()` run then failed with `EBUSY: resource busy or locked` trying to overwrite it). `fileClose()`'s own `globalThis.excelPidsBefore` (captured in `fileOpen()`) is the `before` set for its `Com.killOrphans` call. This is a **standing, universal pattern** — any NEW `Excels.*`/`Word.*`/`PowerPoints.*` method that opens a COM Application object follows the same `before = Com.pidsOf(imageName)` → `try { ... } finally { ...Quit/release...; Com.killOrphans(imageName, before); }` shape, no exceptions. Regression tests: `tests/Excels.test.js` → `Excels.fileClose` (asserts `Com.killOrphans('EXCEL.EXE', globalThis.excelPidsBefore)` is called, including when `Quit()` itself throws) — `Com.killOrphans`'s own kill-diff mechanics are already covered by `tests/Com.test.js`.
- **Excel COM's `Cells.Replace` has a hard 255-character limit on its Replacement argument (VBA "Replacements too long", Error 746) — universal to ANY long `yamlData` value, not one field.** `Excels.replaceInSheet` surfaces a >255-char replacement as `DispInvoke: Replace: DISP_E_TYPEMISMATCH` (winax's marshaling error, not VBA's own error text) — confirmed live via `ComOKEDName` (a ~470-char OKED activity description from `MySoliq.entrepreneurInfo`/`MySoliq.companyInfo`), but the same crash hits any other yaml field that happens to hold a long string, for a YaTT or an ordinary MChJ alike. Fix: `replaceInSheet` checks `String(replace).length > 255` — under the limit, uses `Cells.Replace` as before; over it, locates the placeholder cell via `Cells.Find(search)` (the search string, `"{KEY}"`, is always short so `Find` is unaffected) and sets the cell's `.Value` directly, which has no such length limit. Regression tests: `tests/Excels.test.js` → `Excels.replaceInSheet` (long-value routes through `Cells.Find`+`.Value`, a value exactly at the 255-char boundary still uses `Cells.Replace`, the not-found case).
- **`Word.wordReplace` (the contract-fill path) never opens the template itself — it copies it to a scratch file in `os.tmpdir()` first and opens/edits/saves the copy.** A read-only fallback open (above) is not enough for this method specifically, because `Find.Execute`/`SaveAs` require write access — a read-only doc throws `DispInvoke: Execute The remote procedure call failed.` the moment a replace is attempted. Copying to a scratch file sidesteps the lock entirely (a plain file copy only needs a shared read, regardless of who else has the template open), so the contract template can be edited even while it's open elsewhere. The scratch file is deleted in the `finally` block; the real template is never touched.
- **`Word.makeContract`'s missing-`ContractNum` guard now `return`s after warning.** It used to warn (`Dialogs.warningBox`) and fall straight through to `path.join(contractFolder, data.ContractNum)` with `data.ContractNum === null`, throwing an uncaught `TypeError [ERR_INVALID_ARG_TYPE]` that killed the whole Node process mid-run (a real incident: a fresh company folder with `ContractDate` still blank hit this exact path via `scripts/Word/contract.mjs`). Fixed by adding the missing `return;` — `makeContract` now returns `undefined` and never calls `wordReplace` when there's no `ContractNum`.

### Dialogs / notifications / registry — NO PowerShell (winax COM + cscript/mshta + reg.exe)

`Dialogs`, `Scanner.notify` and `Registry.clean` must **never** shell out to PowerShell. The old PowerShell path invoked `powershell -EncodedCommand <utf16le base64>` via `execSync`/`spawnSync`, and its **UTF-16 stdout leaked into the console byte-swapped**, rendering as garbled "Chinese-looking" glyphs (each 2 ASCII bytes → 1 CJK char). PowerShell is also forbidden by the global rules. Every such call was replaced with a clean, UTF-8 path:

- **`Dialogs.messageBox` / `warningBox` / `errorBox`** → **winax COM** `new (require('winax').Object)('WScript.Shell').Popup(text, secondsToWait=0, title, buttons+icon)` — a native message box that writes **nothing** to stdout. `messageBox(message, title, icon)` takes an optional icon (default `Icons.Information`); `Popup` type = `Buttons.OK (0)` + the icon code.
- **`Dialogs.inputBox` / `openFileDialog`** → **`cscript //nologo <temp .vbs>`** via `execFileSync` (cscript emits clean UTF-8). `inputBox` uses VBScript's built-in `InputBox()`; `openFileDialog` uses the `UserAccounts.CommonDialog` COM object. Shared helper `Dialogs._runVbs(vbsScript)` writes a temp `.vbs` (latin1), runs cscript, returns trimmed stdout, deletes the file; `Dialogs._vbsStr(s)` escapes a JS string into a VBScript literal (doubled `"`, newlines via `& vbCrLf &`).
- **`Dialogs.multilineInputBox`** → **`mshta <temp .hta>`** via `execFileSync`; the HTA writes the entered text to a temp UTF-16 file, which is read back (`fs.readFileSync(..., 'utf16le')`, BOM stripped, CRLF→LF) and deleted. No WinForms, no PowerShell.
- **`Scanner.notify`** → **winax COM** `WScript.Shell.Popup(message, timeoutSeconds, title, type)` (type 64 = Information, 16 = Error).
- **`Registry.clean`** → **`reg.exe`** via `execFileSync` (clean UTF-8), all logic in Node: `reg query` the User (`HKCU\Environment`) and System (`HKLM\…\Session Manager\Environment`) keys (parsed by `Registry._parseQuery` → `[{name, kind, value}]`), drop dead `Path`/`Path_*` tokens (`%VAR%` refs to undefined vars, or literal dirs that no longer exist), `reg add … /t <kind> /d <kept> /f` to rewrite each survivor **preserving its registry type**, `reg export` for the backup (folder `%USERPROFILE%\registry-path-backup-<stamp>`, stamp from `Registry._stamp` = `yyyyMMdd_HHmmss`), and a `rundll32 user32.dll,UpdatePerUserSystemParameters` broadcast. Elevation is inferred from whether an HKLM `reg add` actually succeeds.
- **Tests** (`tests/Dialogs.test.js`, `tests/Scanner.test.js`, `tests/Registry.test.js`) mock these boundaries: **winax** by mocking `node:module`'s `createRequire` (the COM object is loaded via `createRequire('winax')`, which bypasses `jest.unstable_mockModule('winax', …)`), and `cscript`/`mshta`/`reg.exe` via a mocked `child_process.execFileSync` (plus `node:fs` for the temp files).

### `Yamls.fillYamlWithInfo` — TIN-vs-PINFL priority for a sole proprietor (YaTT)

A target folder's `Compan/` can carry **both** a 9-digit TIN marker file (`491842367.txt`/`.app`) **and** a 14-digit PINFL marker file (`31311816590022.txt`) — this happens for a sole proprietor (YaTT) registered under their own personal ID, where the "company" and the individual are the same legal person. `Yamls.fillYamlWithInfo` resolves `comTIN` by checking **`Files.getPINFLFromTXT` first, falling back to `Files.getTINFromTXT`** — the PINFL is the stronger signal (it identifies an individual, never a company with a separate director) and must win when both markers are present.

- **Why the order matters:** Didox's `infoByTinPinfl` lookup keyed on a 9-digit TIN for a sole proprietor returns `directorPinfl: ""` and `director: null` — there is no separate director record, because the entrepreneur _is_ the registered entity. Before this fix, `getTINFromTXT` was checked first, so a YaTT target with both markers present resolved `comTIN` to the 9-digit TIN, `isYatt` stayed `false`, and `DirName`/`SurName`/`SurTIN`/etc. were left permanently blank (the generate step "did nothing" from the user's perspective) while `Compan/null.app` and `Compan/Director null.app` marker files got written as a side effect of `ceo`/`ceo.name` resolving to `null`.
- **`isYatt` is derived from `ComType`, resolved BEFORE `comTIN`'s own resolution order matters for the `#YaTT` marker/`directorPinfl` self-correction** — see the dedicated section below; this section's PINFL-vs-TIN priority for `comTIN` itself is unaffected by that change.
- **A stray `null`/`undefined`-named `.app` marker file found in a `Compan/`/`Contract/` folder is a symptom of this bug having run previously** — it is old, garbled output from before the fix, not a new-format marker. Leave it in place (never delete per the standing "nothing is ever deleted" rule) rather than treating it as intentional data.
- Regression test: `tests/Yamls.test.js` → `Yamls.fillYamlWithInfo` → _"prefers the PINFL marker over the TIN marker when both exist"_.

  YaTT sole proprietor or, for example, the director of an MChJ whose own personal
  PINFL happens to be the marker on file in `Compan/` — length alone cannot
  distinguish these cases. `ComType` is a real, document-grounded fact instead.

### `Files.exists()` — must use the Promise-based `fs.promises.access`, never the callback-style `fs.access`

`Files.exists(filePath)` (in `classes/Files.js`) awaits `access(filePath)` — the **Promise-based** `access` imported from `node:fs/promises`. It must **never** be changed to call `fs.access(filePath)` off the default `fs` import (`import fs from 'fs'`) — that is the **callback-style** API, and calling it with no callback argument throws synchronously (`"cb" argument must be of type function`), which the surrounding `try/catch` silently swallows, making the method **always return `false`** — even for a file that genuinely exists. This exact bug shipped for a real stretch of time and was previously only _documented_ as a known issue in a test title rather than fixed, silently breaking every guard that depends on `Files.exists` (e.g. `Yamls.update`'s template-existence check always failed regardless of whether `Templates.Yaml` pointed at a real file).

### YAML writes never quote a key/value unless it contains a space

Every `.contract`/`config.yml` write in `classes/Yamls.js` goes through `js-yaml`'s `dump()` under `yaml.JSON_SCHEMA`, then `Yamls.#stripUnnecessaryQuotes(dumpedYamlText)` — a post-process that strips the quotes `js-yaml` adds around a plain scalar key/value that doesn't actually need them (e.g. `'2026-03-31': '3200000'` → `2026-03-31: 3200000`). `js-yaml` quotes any scalar that _looks_ like a number/date/bool even when unquoted would round-trip fine; only a value containing a space keeps its quotes (or one that would otherwise misparse — `true`/`false`/`null`/`~`/`yes`/`no`, a leading `#`/`-`/`:`/`?`/`,`/`[`/`]`/`{`/`}`, or an embedded `: `/` #`).

- **Every `yaml.load`/`yaml.dump` call in `classes/Yamls.js` uses `{ schema: yaml.JSON_SCHEMA }`** — `getYamlValue`, `loadAndParseYaml` (already was), `writeYamlArraySection`, `mergeYamlsInFolder`, `setConfig`/its own `yaml.load`. Under `JSON_SCHEMA`, an unquoted date-shaped key/value (`2026-03-31`) stays a plain JS string on reload — it is never resolved into a JS `Date` object the way the DEFAULT schema (`yaml.load(text)` with no options) would resolve it, which would silently corrupt a date used as a map key (`Object.entries(entry)[0]` would then be a `Date`, not the string `"2026-03-31"`). Every reader in this file was switched to `JSON_SCHEMA` together, so date-shaped keys/values stay consistent everywhere, not just in `loadAndParseYaml`.
- **An unquoted numeric-looking value (`'3200000'` → `3200000`) reloads as a JS number, not a string** — deliberately accepted, since every real consumer of these values already does `Number(String(v).replace(/,/g, ''))` before using it (see `Yamls.actualPayments`/`computePaymentChain`/`computeFaktura`/etc.), so the type change is harmless.
- **`Yamls.#stripUnnecessaryQuotes`/`Yamls.#isSafeUnquoted`** are the shared private helpers — any NEW `yaml.dump` call added to this class routes its output through `#stripUnnecessaryQuotes` the same way, never left with `js-yaml`'s raw (over-)quoting.
- `Category.js`'s `loadYaml` (an unrelated file-organizing spec format, keyed by filenames, never date/amount data) and `Scanner.js`'s `toYaml` (a folder-tree scan report, write-only, never read back as a `.contract`) are unaffected — out of scope for this rule.
- Regression tests: `tests/Yamls.test.js` → the `writeAccrual` chaining test, `writeCellArrays`, and `mergeYamlsInFolder` all assert the unquoted shape (a bare digit value now round-trips as a JS number, not a string, per the accepted tradeoff above).

```yaml
    - 2025-09-01: 390,000
```

- **`Dates.monthsBetween(startExcel, endExcel)`** (`classes/Dates.js`) — returns one `{start, end}` range (both `YYYY-MM-DD`) per calendar month from `startExcel` through `endExcel` inclusive. Only **first** range's `start` clamped to real `startExcel` (never forced back to 1st of that month); every range's `end` — including first and last — always runs through **full last day of its own calendar month**, never clamped to real `endExcel`. `buildAccrualEntries` uses `end` internally for proration math only — never carried into the written key.
- **`Dates.monthEnd(dateExcel)`** (`classes/Dates.js`) — last calendar day (`YYYY-MM-DD`) of month containing `dateExcel`. Re-derives a period's real end wherever only its bare start (Accrual's own key) is carried — `applyPriceMaxToDebtMonths`'s own proration re-check, `computePenaltyDays`'s per-period date-range filter.
- **`Yamls.writeAccrual(filePath, accrual)`** (`classes/Yamls.js`) — idempotently inserts/replaces `Accrual:` block right after `ComBase:` line (**not** `ActDateEnd:`, per real incident below — strips any previously-written `Accrual:` block, plus legacy `Pricings:`/`PriceHistory:` key names from earlier development, so old-format file converges to current key/shape on next write); falls back to appending at end-of-file with warning if `ComBase:` missing. Each array item a single bare `"start"`: price mapping — key built in `buildAccrualEntries` as the period's own `start` from a `Dates.monthsBetween` range.
- **Always runs unconditionally inside `Yamls.replaceYaml`**, right after final `replaceTextLine` write loop, over range `yamlData.PeriodStart`..`yamlData.ContractDateEnd` (both YYYY-MM-DD, contract's real active period, already computed earlier in `replaceYaml`) at current `yamlData.Price` — **not** gated behind `Excels.generate`/Excel report generation. Every `Yamls.fillYamlWithInfo`/`Yamls.update` run (normal contract-fill pipeline) writes/refreshes it, regardless of whether Excel `ActReco` file ever produced for that run.
- Regression tests: `tests/Dates.test.js` → `Dates.monthsBetween` (always-full-month-end case, even single-month range) + `Dates.monthEnd`; `tests/Yamls.test.js` → `Yamls.writeAccrual` (legacy `Pricings:`/`PriceHistory:` migration case) + `Yamls.computePenaltyDays` (month-boundary-split case) + `Yamls.replaceYaml` → _"always writes one Accrual entry per month across the contract period"_.

The same 9 keys `Excels.generate` already reads from `config.yml`'s `Excel.CellNames` (used to place `{Bank-OT}`-style placeholders on the `App` sheet of a generated `ActReco` Excel file — confirmed against a real file, `d:\Humans\Building\Rentalls\ActReco\Projects\Act 91.xlsx`, whose row-1 headers read `Начисление`/`Перечисления ООО`/`Возвраты ООО`/`Счет Фактуры`/`Перечисления Физ. лицо`/`Перечисления AR`/`Возвраты AR`/`Залоговая сумма`/`Возвраты залога`/`Распределения` for `Accrual`/`Bank-OT`/`Bank-IN`/`EHF-IN`/`Trans-OT`/`BaaR-OT`/`BaaR-IN`/`Card-OT`/`Card-IN`/`Bonuses` respectively) are **also** written straight into the `.contract` yaml on every fill — the same folder-scan data is no longer Excel-only.

### Every contract date is ONE bare-named YYYY-MM-DD key, filled manually in `ALL.contract`

`ContractDate`, `ContractDateEnd`, `IjaraDateEnd`, `ActDateStart`, `ActDateEnd` are the **only** contract-date keys, each holding **YYYY-MM-DD**, each **filled manually in the `.contract` yaml**. `PeriodStart`/`PeriodEnd` stay purely computed (never input fields). **`PeriodEndApp` is retired** — `PeriodEnd` alone now carries what `PeriodEndApp` used to compute (see the `PeriodEnd` rename section below); `Yamls.deleteScalarLine` strips any stale `PeriodEndApp:` line still sitting in an older real file on the next fill.

- **A blank `ContractDate` auto-fills, address-conditioned — never from a `Compan/` date-marker file.** `Yamls.#resolveContractDate` (called by `replaceYaml`, before `#resolveDates`) reads the company's street address from **MySoliq's own response** — `companyInfo.soliq?.company?.streetName` for a non-YaTT, `companyInfo.soliqYatt?.entrepreneurshipAddress?.address` for a YaTT — **never Didox's own `companyInfo.address` field** (a separate, pre-existing field Didox populates for its own `AddressType`/`Adolat` folder-classification switch in `Didox.infoByTinPinfl`, unrelated to this check). Address contains `"Adolat MFY"` **or** the Cyrillic `"Адолат МФЙ"` spelling (real MySoliq responses come back in Uzbek Cyrillic, e.g. `"Адолат МФЙ, 4 мавзеси, 28/1в-уй"`) → uses that company's real registration date (`companyInfo.soliq?.company.registrationDate` for non-YaTT, `companyInfo.soliqYatt?.registrationDate` for YaTT — both DD.MM.YYYY, converted to YYYY-MM-DD via `Dates.didoxToExcel`); any other address → today's date (`Dates.today()`, a thin `dayjs().format('YYYY-MM-DD')` wrapper). Only fires when `ContractDate` is genuinely blank (`Files.isEmpty`) — a value already typed into `ALL.contract` always wins, never overwritten. The `"ContractDate is missing or invalid"` warning now only fires for a genuinely **invalid** (non-YYYY-MM-DD) value someone typed in by hand, never for blank — blank is always resolved before `#resolveDates` runs its `Dates.splitExcelDate` check.
- **Only two keys are auto-computed, and only when left blank:** `ContractDateEnd` = `ContractDate` + `config.yml`'s `Contract.AddDays` (via the format-preserving `Dates.addDays`), and `IjaraDateEnd` = `config.yml`'s `Contract.IjaraDateEnd`. A value the user typed into `ALL.contract` always wins — each is guarded by `Files.isEmpty`.
- **`Day`/`Month`/`Year` (+ the `End`/`Ijara` twins) are split off those YYYY-MM-DD values by `Dates.splitExcelDate`** — never `Word.extractDate`, which only ever parsed DD.MM.YYYY. They remain load-bearing: `Day`/`Month`/`Year` feed `Word.contractNumFromFormat`'s `{Prefix}-{ComName}-{Year}-{Month}-{Day}` contract number, and all nine are Word-template placeholders.
- **`Dates.addDays` is format-preserving** — YYYY-MM-DD in yields YYYY-MM-DD out, DD.MM.YYYY in yields DD.MM.YYYY out — so its standalone runner and any DD.MM.YYYY caller keep working unchanged. `Dates.isExcelDate`/`Dates.splitExcelDate` are its YYYY-MM-DD companions.
- **DD.MM.YYYY still exists at genuine external boundaries, and stays there:** the `Compan/` marker files on disk (`29.03.2017.app`, read by `Files.getDateFromTXT`) and every registry-API date (`ComVATDateReg`, `ComRegDate`, `ComReRegDate`, parsed by `Dates.parseDMY`). `ContractDate` itself is compared via `Dates.parseDMYExcel` in the VAT check.
- **`config.yml`'s `Contract.IjaraDateEnd` is YYYY-MM-DD** (`2029-12-31`). `Dates.didoxToExcel`/`excelToDidox` are both idempotent (each regex simply will not match the other format), so either is safe to use as a normalizer on an externally supplied date.
- **Every field name states what it actually is, not `Com*`/generic `Future*`/`Start*`.** `Com*` is reserved for the **company** (`ComINN`, `ComName`, `ComBank`, `ComRegDate`) — a contract-scoped date under that prefix was easy to confuse with a real company fact, and `ComDate` sitting beside `ComRegDate` (the company's real registration date) was actively misleading whenever the two differ (they do for `ASHALIFE PHARMA`: `ContractDate: 2026-01-01` vs. `ComRegDate: 09.07.2025`). `PeriodStart`/`PeriodEnd` name the reconciliation window they bound (fed straight into `recomputeChain`/`buildAccountEntries`), not "future"/"start" in the abstract.
- **A pre-existing real `.contract` file carrying `_`-suffixed lines needs a one-time cleanup**: delete its old `ComDate_`/`ComDateEnd_`/`ComDateIjara_`/`ActDate_`/`ActDateEnd_` lines — the bare-named keys already hold the same dates in YYYY-MM-DD. Done for all three real files this project tracks (`NETORA TECHNOLOGY GROUP`, `ASHALIFE PHARMA`, `YaTT RYABSEV OLEG VLADIMIROVICH`), whose `PeriodStart`/`ContractDateEnd`/`PeriodEnd` also sit below the `#################` divider, right after `ContractNum`.
- Regression tests: `tests/Yamls.test.js` → `Yamls.replaceYaml`'s date tests (`ContractDate` auto-fill-from-today, auto-fill-from-MySoliq-registrationDate for Latin AND Cyrillic `"Adolat MFY"`/`"Адолат МФЙ"` addresses, YaTT `entrepreneurshipAddress` variant, never-overwrites-an-already-filled-`ContractDate`, `ContractDateEnd` computed-when-blank, `ContractDateEnd` user-set-wins, `ContractDateEnd`/`IjaraDateEnd` missing-or-invalid); `tests/Dates.test.js` → `Dates.addDays`'s YYYY-MM-DD format-preservation + `Dates.isExcelDate` + `Dates.splitExcelDate` + `Dates.today`.

### `Yamls.replaceYaml` is a thin orchestrator over four private stages, each failing loudly

`replaceYaml` is ~25 lines: two guards, then `Yamls.#resolveContractDate` → `Yamls.#resolveDates` → `Yamls.#resolveCompany` → `Yamls.#writeChain`. Each stage is independently readable and independently testable through `replaceYaml`'s own public surface. `replaceYaml` itself returns `true` on full success and `false` on every abort path (missing `yamlData`/`companyInfo`, missing `Price`, or any stage returning `false`) — `fillYamlWithInfo` forwards this boolean to its own caller, so a runner (`scripts/Word/contract.mjs`, `scripts/Excels/contract.mjs`, `scripts/Yamls/contractUpdate.mjs`) can skip its own follow-up COM/Excel step when the fill genuinely didn't complete, instead of running that step against a still-half-empty yaml.

- **`#resolveContractDate(yamlData, companyInfo)`** — auto-fills a blank `ContractDate` (see the "Every contract date" section above for the full address-conditioned rule); never touches an already-filled value. Runs first, since `#resolveDates` requires `ContractDate` to already be a valid YYYY-MM-DD.
- **`#resolveDates(yamlData)`** — fills `IjaraDateEnd`/`ContractDateEnd` when blank, splits `Day`/`Month`/`Year` (+ `End`/`Ijara` twins) off the YYYY-MM-DD values, derives `PeriodStart`/`PeriodEnd`. Returns `false` on the first unresolvable date so the caller aborts **before** anything is written.
- **`#resolveCompany(ymlFile, yamlData, companyInfo)`** — every company/director/bank/VAT field, `ComCategory` from the file's own path, and the `Compan/` marker writes.
- **`#writeChain(ymlFile, yamlData)`** — the `replaceTextLine` persist loop, then the whole `Accrual`→`Payment`→`Faktura`→`Loaners`→`PenaltyDays`→`Penalty`→`Returns` chain and every `Excel.CellNames` block.
- **Three fail-loudly guards replaced three silent-wrong-answer paths:**
    - **`Price`** is validated at the very top, before the first marker file or yaml line is written — it is read much later as `String(Price).replaceAll(...)`, so a missing `Price` used to throw _after_ markers and yaml lines were already on disk, leaving the contract half-updated.
    - **`PrepayMonth`** — `Yamls.getPrepayMonth` returns `null`, never `NaN`, when neither `yamlData.PrepayMonth` nor `config.yml`'s `Contract.PrepayMonth` resolves to a whole month count. A `NaN` used to reach `Dates.futureDateByMonth`, produce dayjs's literal `"Invalid Date"` for `PeriodEnd`, and empty the whole chain with `Penalty` reading `0`. `null` is fatal **only** when `ActDateEnd` is blank — with `ActDateEnd` filled, `PeriodEnd` comes straight off it and `PrepayMonth` is never read.
    - **VAT `ComVATFromUs`** — `ContractDate` (`Dates.parseDMYExcel`, YYYY-MM-DD) and `ComVATDateReg` (`Dates.parseDMY`, DD.MM.YYYY straight from the registry API) are both validity-checked before comparing. Either parser yields an `Invalid Date` for blank input, and **every** comparison against an `Invalid Date` is `false`, so the unchecked compare fell through and asserted `'Нет'` — a real answer invented from unparseable input. Unknown now stays unknown: blank `ComVATFromUs`, no `#VAT-From-Us` marker. Confirmed live on `NETORA TECHNOLOGY GROUP` (real `ComVATRegCode: 326030326950`, blank `ComVATDateReg`), which flipped from `Нет` to blank.
- **`Files.getDateFromTXT` and `Word.extractDate` are KEPT as standalone public utilities** even though `classes/` no longer calls either — same explicit decision already recorded for `Excels.scanSubFolder`/`scanSubFilesTxt`. Each keeps its own `scripts/` runner, `sheller/` entry and tests, and each is still genuinely useful on its own (`getDateFromTXT` reads a `Compan/` DD.MM.YYYY marker; `Word.extractDate` parses a DD.MM.YYYY registry-API date). Nothing was deleted — removing public API surface needs an explicit ask.

### `Excels.js` reads pricing/transaction data straight from the .contract yaml — no more folder-scanning

`Excels.processPricing` and `Excels.processFolders` used to scan `Pricings/`/`<Excel.CellNames-key>/` subfolders on disk for `"YYYY-MM-DD amount"`-named entries. Since `Yamls.replaceYaml` now writes this exact data into the `.contract` yaml itself (`Accrual`, per the section above, and every `Excel.CellNames` key, per the section above that), `Excels.js` reads it from there instead — the `.contract` yaml is the single source of truth; the folder scan is retired from this path.

- **`Excels.processPricing(yamlData)`** — reads `yamlData.Accrual` (an array of bare `{"start": price}` mappings) and writes one row per entry (the start date + the price) starting at the `{Pricings}` placeholder's cell — no `globalThis.folderPricings`/`scanSubFilesTxt` call anymore.
- **`Excels.processFolders(entries, found)`** — signature changed from `(folder, found)` (folder name + on-disk scan) to `(entries, found)` (an already-resolved `[{date: amount}]` array) — writes one row per entry starting at `found`'s cell. `Excels.generate`'s own loop over `Excel.CellNames` now reads `yamlData[cellName]` directly (already populated by `Yamls.writeCellArrays`) instead of checking `fs.existsSync(path.join(globalThis.folderALL, cellName))` and scanning that folder.
- **`Excels.scanSubFolder`/`Excels.scanSubFilesTxt` remain as standalone utility methods** (still public, still tested, still runnable) — they are simply no longer called internally by `processPricing`/`processFolders`; nothing else in this project currently uses them, but they were not deleted since removing public API surface wasn't asked for.
- Regression tests: `tests/Excels.test.js` → `Excels.processPricing` (writes from `yamlData.Accrual`, no-op on empty/missing) + `Excels.processFolders` (writes from a passed-in entries array) + `Excels.generate` (its `Excel.CellNames` loop reads `yamlData[cellName]`).

### `Accrual`/`History`/`Payment`/`Faktura`/`Loaners`/`PenaltyDays`/`Penalty`/`Returns` — the code-driven chain (see the fuller rental-reconciliation rule block below for the calculation rules; this section documents the concrete implementing code)

`Yamls.fillYamlWithInfo` writes all eight blocks on every contract fill via `Yamls.recomputeChain` + `Yamls.computeFaktura`/`computeFakturaSend` + `Yamls.computeDailyBalance`/`computePenaltyDays`/`computePenalty` (`classes/Yamls.js`) — **NOT** `computePunish`/`writePunish`, which no longer exist in this codebase (an earlier draft of this documentation described that shape; it was superseded by the chain below and never matched the shipped code):

- **`Yamls.recomputeChain(startDate, futureDate, priceMon, payments)`** — **signature changed** (see the dedicated `PriceMon`/`PriceMaxMon` architecture-reversal section above): builds `Accrual` by reading each month's own rate off `priceMon` via `buildAccrualEntries`, chains real `payments` across it via `computePaymentChain` to get `Loaners` (and an internal `payment`, no longer written to the yaml as-is — see `Payment:` below). **The old fixed-point loop over `applyPriceMaxToDebtMonths` is GONE** — `PriceMon` no longer varies by debt, so there is nothing left to converge on; `Accrual` is built once and chained once. Appends a trailing `{ ALL: sum }` entry to `accrual`/`loaners`/`payment`. `payments` passed in is `Bank-OT + Trans-OT + Card-OT + BaaR-OT` (see `actualPayments`/the inline scan in `replaceYaml`).
- **`Payment:` WRITTEN to the yaml is a SEPARATE, FLAT date-keyed merge — NOT `recomputeChain`'s own per-period chain output.** `Yamls.mergeDateKeyedArrays(bankOT, cardOT, baarOT, transOT)` merges the four raw `-OT` scans into one array, one entry per distinct date, summing amounts when the same date appears in more than one source (e.g. a Bank-OT and a Card-OT payment on the same day are added together) — shape `[{ '2026-04-21': '1,600,000' }, ...]`, no `#` interval key — `Yamls.writePayment` appends its own trailing `{ ALL: sum }` via `Yamls.appendAllTotal` right before writing (`mergeDateKeyedArrays` itself never appends one, so `recomputeChain`'s internal consumer of the pre-total flat array is unaffected). `Yamls.writePayment` writes this flat array, not `recomputeChain`'s chain-allocated one. `Loaners`/`PriceMax` re-pricing still use the internal chain-allocated figure — the two `Payment` representations (internal chain vs. written flat merge) are intentionally decoupled; `Payment[i] + Loaners[i] === Accrual[i]` **no longer holds** for the written `Payment:` key (it held for the pre-2026-08 chain-allocated shape, not this one).
- **`Returns:`** — the `-IN` counterpart of `Payment:`, same flat-merge mechanism: `Yamls.mergeDateKeyedArrays(bankIN, cardIN, baarIN)` merges `Bank-IN + Card-IN + BaaR-IN` (deliberately excluding `Trans-IN`, which has no dedicated `Excel.CellNames`/scan-folder key in this project). Written via `Yamls.writeReturns`, anchored directly after `Penalty:`.
- **`History:`** — `Yamls.computeHistory(payment, returns)` merges the already-flat `Payment:` and `Returns:` arrays into ONE flat date-keyed array: a `Payment` amount is carried as-is (positive), a `Returns` amount is negated; a date present in both sums together (Returns already negative), so a same-day payment+return nets out. Sorted by date — `Yamls.writeHistory` appends its own trailing `{ ALL: sum }` via `Yamls.appendAllTotal` right before writing (`computeHistory` itself never appends one, so `buildAccountEntries`'s own per-day lookup off the pre-total array is unaffected). Written via `Yamls.writeHistory`, anchored directly after `Accrual:`, before `Payment:` — `writePayment`'s own fallback anchor was moved from `Accrual` to `History` to keep this position. Verified end-to-end via a real `fillYamlWithInfo` run against `NETORA TECHNOLOGY GROUP\ALL 4.contract`: `History:` landed between `Accrual:`/`Payment:` with every `Payment` date carried through unchanged and the one same-date `Returns` entry (`2026-01-24: 1,600,000`) written back negated (`'-1,600,000'`, quoted — a leading `-` needs quoting under `#isSafeUnquoted`, same as any other YAML-special leading character).
- **`Yamls.computeDailyBalance(startDate, futureDate, accrual, payment, returns)`** — a prepaid running-balance simulation (contract §21.1 + §3.7/§1.20), day by day from `startDate` through `futureDate` inclusive: each calendar day debits that day's pro-rated share of its own month's `Accrual` (`monthAccrual / daysInMonth`), credits any `Payment` entry landing that exact date, and debits any `Returns` entry landing that exact date. Returns `[{ date, debit, credit, balance }, ...]`, one entry per day. **No longer called from `Yamls.#writeChain`** — `computePenaltyDays` now reads `Account` directly (the same daily ledger written to the `.contract` yaml, keyed by `PriceDay`-debited balances rather than pro-rated-`Accrual`-debited ones) instead of this separate internal simulation. Kept as a standalone public method (own runner, own tests) per the "don't delete public API surface without being asked" rule. **Guards against a malformed/unresolvable `startDate`/`futureDate` (e.g. dayjs's literal `"Invalid Date"` string, which sorts lexically AFTER any real ISO date and would otherwise make the day-stepper loop run forever)** — both bounds are validated against a strict `YYYY-MM-DD` regex and `startDate <= futureDate`; on failure, returns `[]` with a warning instead of looping. A second hard backstop (`MAX_DAYS = 50000`, ~137 years) guards any other unforeseen non-terminating case. Real incident: a jest test's isolated mock `config.yml` omitted `Contract.PrepayMonth`, so `Dates.futureDateByMonth(NaN, false)` produced `"Invalid Date"` for `PeriodEnd`, and the very first version of this function looped until the Node process ran out of heap (`FATAL ERROR: Reached heap limit`) — caught by running the suite for real, not by reasoning about the code in isolation.
- **`Yamls.computePenaltyDays(account)`** — reads `Account:` directly (the array `buildAccountEntries` produces/`writeAccount` writes), one signed-balance entry per calendar day. **The 1-calendar-day grace period from §3.7/§1.20 applies EXACTLY ONCE, to `Account`'s own very first entry (index 0, `PeriodStart`'s own day) — never re-granted, no matter how many separate deficit streaks occur later.** Every OTHER calendar day the balance is negative counts toward `PenaltyDays`, including the first day of a brand-new deficit streak that starts after the balance had recovered to `>= 0` — a balance recovering and then going negative again does NOT earn a fresh grace day (confirmed via real user correction: `Account` showed 14 consecutive negative days in 2026-06, `PenaltyDays` must show 14, not 13). **Returns one bare `"YYYY-MM"`-keyed entry per calendar month `Account` covers**, plus a trailing `{ ALL: sum }` — same key shape as `PriceMon`/`PriceDay`, not `Accrual`/`Loaners`.
- **`Yamls.computePenalty(penaltyDays, penaltyForDay, priceMaxMon)`** — **signature changed again**: `Penalty[month] = PenaltyDays[month] * penaltyForDay`, capped at HALF that month's own `PriceMaxMon` amount (`priceMaxMon[month] / 2`) — a month whose raw multiplication would exceed the cap is clamped down to the half-`PriceMaxMon` figure instead. A month with no matching `PriceMaxMon` entry has a `0` cap (`0` penalty), matching the same "missing entry treated as 0" convention every other chain lookup in this file uses. This reintroduces a cap concept (the earlier %-of-`Accrual` `CapRatio` model was fully retired, then this new PriceMaxMon/2 cap was added on top of the resurrected `PenaltyDays * PenaltyForDay` multiplication — two separate corrections, not a revert). `penaltyForDay` resolution in `replaceYaml`: `yamlData.PenaltyPerDay` (a per-contract starting-Variable field, sits directly after `Tariff:`, bundled blank by default like `ContractNumber`) when non-empty (`Files.isEmpty`) — else falls back to `config.yml`'s global `Penalty.PerDay` (default `50000`, contract §21.1's fixed daily rate). Same blank-vs-filled precedence shape as `ContractNumber`/every other out-of-scope starting-Variable field — never asked about, never auto-filled by `smarts-firm-docums`'s `contract-dot` action, purely a manual per-company override when the standard rate doesn't apply.
- **`Yamls.computeFaktura(accrual, ehfIn)`** — distributes the real `EHF-IN` invoice sum (an issued invoice, not cash) across the **final**, already-`recomputeChain`-settled `accrual` periods, by reusing `computePaymentChain`'s own chaining logic and keeping only its `payment` half (a period's own `Loaners`-vs-invoice split has no meaning for an invoice document). Each period is capped at its own `Accrual` amount; once the whole `EHF-IN` sum is exhausted, every remaining period gets `0`. Must run against `recomputeChain`'s **returned** `accrual` (the fixed-point one, already re-priced at `PriceMax` on any debt month) — never the pre-recompute baseline. **The chained result's key is remapped from `Accrual`'s own bare START date to that same period's bare END date via `Dates.monthEnd`** (`e.g. Accrual`'s `2026-01-19` → `Faktura`'s `2026-01-31`) — an invoice document is dated by when its own billing period closes, never by when it opened; every OTHER chain block (`Loaners`/`PenaltyDays`/`Penalty`) stays keyed on the start date, unaffected. Appends its own trailing `{ ALL: sum }`. Unaffected by the `Payment`/`Penalty` model change above.
- **`Yamls.computeFakturaSend(accrual, ehfIn)`** — per-period amount NOT YET invoiced: `Accrual[period] - Faktura[period]` (an invoice is always eventually sent for the full `Accrual` amount; `FakturaSend` is the shortfall still owed). Reuses `computePaymentChain`'s `loaners` half (the same `owed - paid` math `computeFaktura`'s `payment` half is built from) rather than recomputing the subtraction — same `Dates.monthEnd` key remap as `computeFaktura`, so `Faktura`/`FakturaSend` always share the same key for the same period (`Faktura[i] + FakturaSend[i] === Accrual[i]` always holds). `Yamls.writeFakturaSend` writes `FakturaSend:` directly after `Faktura:`, one blank line between them.
- **`Yamls.actualPayments(yamlData)`** — real incoming cash for the internal debt chain: `Bank-OT` + `Trans-OT` + `Card-OT` + `BaaR-OT` (`BaaR-OT` added; was previously `Bank-OT` + `Card-OT` only per an even earlier doc draft, then `Bank-OT`+`Trans-OT`+`Card-OT`). `EHF-IN` (an invoice, not cash), `Bank-IN`/`Card-IN`/`BaaR-IN` (refunds — see `Returns`), `Bonuses` are excluded.
- **`Yamls.mergeDateKeyedArrays(...arrays)`** — the shared flat-merge primitive both `Payment:` and `Returns:` are built from: merges N date-keyed arrays into one, summing amounts on a same-date collision across sources, sorted by date, no trailing `{ ALL }` (callers append their own if needed).

### `Account` — client's own daily running balance, one entry per calendar day, written directly after `History:`

`Account:` is a daily-granularity companion to `PriceDay`/`History` — a `"YYYY-MM-DD"`-keyed array, one entry per calendar day from `PeriodStart` through `PeriodEnd` inclusive, holding the client's own account balance for that exact day:

```yaml
Account:
  - 2026-01-19: 1,600,000
  - 2026-01-20: 1,547,742
  - 2026-01-21: 1,495,484
```

- **`Yamls.buildAccountEntries(startDate, futureDate, history, priceDay, priceMaxDay)`** — every day, INCLUDING day 1 (`startDate`, i.e. `PeriodStart`), debits off the PREVIOUS day's balance (day 1's own "previous balance" is `0`), then adds that day's own `History` entry: `balance = previousBalance - debitRate + (History[thatDay] ?? 0)`. **The debit rate itself depends on the PREVIOUS day's own balance sign — `PriceDay[thatDay'sMonth]` (the prepay discount) when the previous balance was `>= 0`, `PriceMaxDay[thatDay'sMonth]` (the full rate, no discount) when the previous balance was already negative.** Business reason: `Price`/`PriceDay` is a discount granted only for genuine prepayment — once a client is in debt, they haven't prepaid, so the next day's own charge reverts to the undiscounted `PriceMax`/`PriceMaxDay` rate until the balance recovers to `>= 0` again. `History` already carries a payment as a positive amount and a return as a negative one (per `computeHistory`), so adding it is a plain add, never a separate credit/debit split. Rent accrues from day 1 onward — an unpaid day 1 already shows a negative balance (at the `PriceDay` rate, since day 1's own "previous balance" of `0` is `>= 0`), same as any other day; there is no day-1 debit exemption. Same invalid-date guard and `MAX_DAYS` backstop as `computeDailyBalance`.
- **`Yamls.writeAccount`** — thin `writeYamlArraySection` wrapper, fallback anchor `History:` (first-ever-insert only). **This anchor collides with `writeLoaners`'s and `writePayment`'s own `History:` anchor on a brand-new file** — `writeYamlArraySection`'s fallback logic inserts right after `afterKey`'s CURRENT block extent, so whichever of three same-anchored keys is written LAST ends up closest to `History:`. `#writeChain`'s real call order (`writeAccount`, then `writeLoaners`, both before `writePayment` already ran) yields `History → Loaners → Account → Payment` on a brand-new file. An already-populated real file keeps its own real position regardless (per `writeYamlArraySection`'s order-preserving contract) — the real `NETORA TECHNOLOGY GROUP` file has `Loaners:` then `Account:` then `Payment:`, directly after `History:`, matching this exact fallback order.
- **Always runs unconditionally inside `Yamls.#writeChain`**, after `priceDay`/`priceMaxDay` are both computed (since `buildAccountEntries` needs both) and after `history` (computed earlier, right before `writeHistory`) — all three are already in scope by the time `Account` is built, no extra folder scan needed. **`Loaners` is derived from `Account` right after it's built** (see the `Loaners` section below), and **`PenaltyDays`/`Penalty` compute AFTER `Account`** (moved down from their old position right after `Loaners:`), since `computePenaltyDays` now reads `Account` directly instead of a separate `computeDailyBalance` simulation.
- Regression tests: `tests/Yamls.test.js` → `Yamls.buildAccountEntries` (day-1-uses-PriceDay, day-1-goes-negative-when-unpaid, switches-to-PriceMaxDay-once-previous-day-negative, switches-back-to-PriceDay-once-recovered, Returns-already-negative case, current-day's-own-month PriceDay/PriceMaxDay lookup, invalid-date-guard cases) + the chained-write ordering test (`writeAccount`/`writeLoaners` called after `writePayment`, lands between `History:`/`Payment:` on a new file) + `Yamls.replaceYaml` → the "always writes one Accrual entry per month" test's `Account` assertions.

### `Loaners` — a plain scalar now, the client's own outstanding debt at `PeriodEnd`

`Loaners:` was an array (one entry per `Accrual` month) before this change — it is now a SINGLE scalar line, written right after `History:` (before `Account:`):

```yaml
Loaners: 893,342
```

- **Value = the ABSOLUTE value of `Account`'s own LAST entry** (i.e. the balance at `PeriodEnd`) — computed inline in `#writeChain` right after `account` is built: `Math.abs(Number(String(lastAccountEntry).replace(/,/g, '')) || 0).toLocaleString('en-US')`. A negative last-day balance (debt) and a positive one (surplus/prepaid) both write the same non-negative magnitude — `Loaners:` never carries a sign.
- **`Yamls.writeLoaners(filePath, loanersTotal)`** — thin `Yamls.writeScalarSection` wrapper (the scalar sibling of `writeYamlArraySection`, see below), fallback anchor `History:`.
- **`recomputeChain`'s OWN internal `loaners` array (used by `buildPriceMonEntries`/`applyPriceMaxToDebtMonths` for the per-month `Price`-vs-`PriceMax` debt-conditioned re-pricing switch) is completely UNCHANGED and UNRELATED to the written `Loaners:` scalar** — same decoupling pattern already established for `Payment` (internal chain-allocated array vs. written flat merge). The per-month debt check that drives `Accrual`/`PriceMon` re-pricing still needs per-month granularity; only the persisted top-level `Loaners:` key collapsed to one number.
- **`Yamls.writeScalarSection(filePath, key, value, afterKey)`** — new generic writer, the scalar counterpart of `writeYamlArraySection`: an existing `"Key:"` line updates STRICTLY IN PLACE; a genuinely new key falls back to inserting `"Key: value"` directly after `afterKey`'s own block, same one-blank-line-on-each-side rhythm. No array-dump/quote-stripping machinery — just a plain `${key}: ${value}` line.
- **`Excels.processLoaners`'s array-shaped `{Loaners}` row loop is now permanently a no-op** for every real contract, since `yamlData.Loaners` is a scalar and `Array.isArray()` guards it to `[]` — kept as standalone dead-shape handling rather than deleted (public API surface isn't removed without being asked). Any real `{Loaners}` placeholder cell is filled by `Excels.generate`'s own generic scalar-replace pass instead (the same pass that fills `{ContractDate}`/etc.), which already skips array-valued keys.
- Regression tests: `tests/Yamls.test.js` → `Yamls.writeScalarSection` (in-place update, insert-after-anchor, append-at-end-when-anchor-missing) + `Yamls.writeLoaners` (writes a scalar line, never an array block) + the chained-write ordering test + `Yamls.replaceYaml` → the "always writes one Accrual entry per month" test's `Loaners` assertion (matches `/^Loaners: '?[\d,]+'?$/m`, never an array).

### `PeriodEnd` — the reconciliation window's real closing date; `PeriodEndApp` is retired

`PeriodEnd` used to be a PAIR of fields — `PeriodEnd` (an EXCLUSIVE upper bound: the first day of the target month) and `PeriodEndApp` (`Dates.getMinusOneDay(PeriodEnd)` — the real last day of the period). Only `PeriodEndApp` was ever the genuinely useful "when does this period actually end" value; `PeriodEnd` itself was a plumbing intermediate. **The pair collapsed into ONE field, `PeriodEnd`, now holding what `PeriodEndApp` used to compute:**

```yaml
PeriodEnd: 2026-08-31
```

- **`Yamls.#resolveDates`'s new derivation** — when `ActDateEnd` is blank: `yamlData.PeriodEnd = Dates.getMinusOneDay(Dates.futureDateByMonth(prepayMonth, false))`. `Dates.futureDateByMonth(prepayMonth, false)` still returns the exclusive bound (first day of the target month) as an internal intermediate — never assigned to `yamlData` — then `Dates.getMinusOneDay` converts it to the real last day of the PRECEDING month. E.g. today `2026-08-17`, `PrepayMonth=1` → `futureDateByMonth` gives `2026-09-01` (internal only) → `PeriodEnd = 2026-08-31`. `PrepayMonth=3` → `2026-11-01` (internal) → `PeriodEnd = 2026-10-31`.
- **When `ActDateEnd` IS filled: `yamlData.PeriodEnd = yamlData.ActDateEnd` directly, NO `getMinusOneDay` shift.** `ActDateEnd` is already a real, explicit end date typed by a human — not an exclusive bound like `futureDateByMonth`'s output — so shifting it back a month would silently make the period end a full month too early. (The OLD `PeriodEndApp` DID apply this shift even to an explicit `ActDateEnd`, which was a latent bug that simply never surfaced, since nothing downstream read `PeriodEndApp` on the `ActDateEnd`-filled path before this rename made `PeriodEnd` itself load-bearing.)
- **Every downstream consumer already read `yamlData.PeriodEnd` unchanged** — `recomputeChain`, `buildAccountEntries`, `Excels.generate`'s `{PeriodEnd}` placeholder — so this rename needed ZERO changes to any call site; only `#resolveDates`'s own derivation changed. `Accrual`'s own last entry, and `Faktura`/`FakturaSend` (both derived from `Accrual`'s own periods via `Dates.monthsBetween`), automatically stop one calendar month earlier than before as a direct consequence — no separate fix needed there either.
- **`Yamls.deleteScalarLine(filePath, key)`** — new generic remover, strips an obsolete `"Key:"` scalar line if present (no-op if the key never existed), collapsing a resulting doubled blank line back to one. `#writeChain` calls `Yamls.deleteScalarLine(ymlFile, 'PeriodEndApp')` right after the generic scalar-replaceTextLine loop, so every already-populated real file gets its stale `PeriodEndApp:` line removed on its very next fill — the generic loop itself never re-writes `PeriodEndApp` since `#resolveDates` no longer sets it on `yamlData`, but the OLD line would otherwise still round-trip forever untouched.
- Regression tests: `tests/Yamls.test.js` → `Yamls.replaceYaml`'s `ContractDateEnd`/`ActDateEnd` date tests (the `ActDateEnd`-explicit case now asserts `PeriodEnd` equals `ActDateEnd` verbatim, no shift) + `Yamls.deleteScalarLine` (removes an existing line and collapses the doubled blank, no-op when missing).

### `PrepayMon` — the actual resolved `PrepayMonth` value the code used, written after `ContractDateEnd:`

A new scalar output field recording the exact `PrepayMonth` value `Yamls.getPrepayMonth` resolved and the rest of the chain (`PeriodEnd` when `ActDateEnd` is blank) actually used — `yamlData.PrepayMonth` when set, else `config.yml`'s `Contract.PrepayMonth`:

```yaml
PrepayMon: 1
```

- **Resolved inside `Yamls.#resolveDates`, immediately after `Yamls.getPrepayMonth(yamlData)` runs** — `yamlData.PrepayMon = prepayMonth ?? ''` (blank when unresolvable/invalid, matching every other out-of-scope starting-Variable field's blank-default convention).
- **Written via `Yamls.writeScalarSection(ymlFile, 'PrepayMon', yamlData.PrepayMon, 'ContractDateEnd')` inside `#writeChain`, right after the generic scalar-replaceTextLine loop** — NOT by that generic loop itself, since `replaceTextLine` only updates an EXISTING line and a fresh `.contract` template doesn't carry this output field yet; `writeScalarSection` inserts it if missing.
- **Purely informational/debug — never read back by any code path.** It exists so a human (or a future audit) can see, without re-deriving the precedence logic by hand, exactly which month count the chain actually computed `PeriodEnd` from for that fill.
- Regression tests: `tests/Yamls.test.js` → `Yamls.replaceYaml` → the "always writes one Accrual entry per month" test's `PrepayMon` assertion (present, blank in that fixture since `ActDateEnd` was filled and `PrepayMonth` was never read).

### `PriceMon`/`PriceMaxMon` are the PERMANENT SOURCE OF TRUTH for every month's own rent rate — `Accrual`/`Account`/`Loaners`/`PriceDay`/`PriceMaxDay` all read from here, never from the flat `Price`/`PriceMax` scalar directly

**Architecture reversal (explicit user instruction).** `PriceMon`/`PriceMaxMon` used to be DERIVED from `Accrual` (built after it, reading `Accrual`'s own debt-conditioned amount per period). This is now inverted: `PriceMon`/`PriceMaxMon` are built FIRST — directly from `yamlData.Price`/`yamlData.PriceMax`, one flat entry per calendar month across `PeriodStart`..`PeriodEnd`, with **no debt-based switching between `Price` and `PriceMax` anymore** — and `Accrual` (via `recomputeChain`/`buildAccrualEntries`) now reads its own per-month rate FROM `PriceMon`. `Price`/`PriceMax` (the flat `yamlData` scalars) exist for exactly ONE purpose now: building/extending `PriceMon`/`PriceMaxMon` themselves — every other calculation (`Accrual`, `Account`'s daily debit rate via `PriceDay`/`PriceMaxDay`, `Loaners`) reads its price from `PriceMon`/`PriceMaxMon`, never `Price`/`PriceMax` directly. User's own words: `"priceMon va PriceMaxMon lar faqatgina oxirgi price va pricemax value dan SubKeys generate qioladi... hamma hisob kirob, Accrual, account loaners, pricedays, maxdays va h.k. lar shu priceMon va PriceMaxMon ning set qilingan valuelarini ishlatishi kerak in all calculations!"` (PriceMon/PriceMaxMon generate their sub-keys only from the last Price/PriceMax value; every calculation — Accrual, Account, Loaners, PriceDay, PriceMaxDay — must use PriceMon/PriceMaxMon's own set values).

**`PriceOK: true` freezes every existing `PriceMon`/`PriceMaxMon` month at its own on-disk value.** Default `PriceOK: false` (or unset) — the whole block is rebuilt fresh from `Price`/`PriceMax` every run, same as before this flag existed. Once set to `true`, `Yamls.freezePriceMonEntries(existing, freshlyBuilt, priceOK)` keeps EVERY existing month (as loaded from the file, hand-edited or not) unchanged, and appends only NEW months strictly after the existing block's own last month, computed from the CURRENT `Price`/`PriceMax`. Why: a company renting for years has its rate change yearly (or more often) — `PriceOK: false` lets `PriceMon`/`PriceMaxMon` regenerate from the current flat `Price`/`PriceMax` on every fill (fine for a fresh/simple contract); once the user has hand-edited each month's own historical rate to match reality, `PriceOK: true` locks that history in place forever — new months still auto-append at the current rate, but nothing already on disk is ever silently overwritten again.

```yaml
PriceOK: true

PriceMon:
  - 2026-01: 1,600,000
  - 2026-02: 1,700,000
  - 2026-06: 1,620,000
  - 2026-07: 1,620,000   # <- newly appended, current Price
  - 2026-08: 1,620,000   # <- newly appended, current Price

PriceMaxMon:
  - 2026-01: 1,650,000
  - 2026-06: 1,650,000
  - 2026-07: 1,650,000   # <- newly appended, current PriceMax
  - 2026-08: 1,650,000   # <- newly appended, current PriceMax

PriceDay:
  - 2026-01: 51,613
  - 2026-06: 54,000

PriceMaxDay:
  - 2026-01: 53,226
  - 2026-06: 55,000
```

- **`Yamls.buildPriceMonEntries(startDate, futureDate, price)`** — one flat entry per calendar month across `startDate..futureDate`, value = `price` verbatim (never prorated, never debt-conditioned — no `Accrual`/`Loaners` input at all anymore). `buildPriceMaxMonEntries(startDate, futureDate, priceMax)` is the same shape against `priceMax`.
- **`Yamls.freezePriceMonEntries(existing, freshlyBuilt, priceOK)`** — `priceOK !== true` → returns `freshlyBuilt` unchanged (the default, always-recompute path). `priceOK === true` → keeps every month in `existing` (ignoring its own trailing `{ALL}` entry) up through its own last real month, appends only `freshlyBuilt` entries whose month sorts strictly after that last month. `existing` empty/`ALL`-only/not an array → falls back to `freshlyBuilt` (nothing to freeze yet).
- **`Yamls.#priceMonLookup(priceMon)`** (private) — builds a `"YYYY-MM" -> number` `Map` from a `PriceMon`/`PriceMaxMon`-shaped array, ignoring the trailing `{ALL}` entry. The one shared primitive every downstream reader (`buildAccrualEntries`, `applyPriceMaxToDebtMonths`) uses to look up a month's own rate.
- **`Yamls.buildAccrualEntries(startDate, futureDate, priceMon)`** — SIGNATURE CHANGED: third argument is now the `PriceMon`-shaped array, not a flat `price` scalar. Each month's un-prorated rate comes from `#priceMonLookup(priceMon).get(monthKey)`; the partial-first/last-month proration math is unchanged (round to nearest whole so'm, never to the nearest 1,000).
- **`Yamls.applyPriceMaxToDebtMonths(accrual, loaners, startDate, priceMaxMon)`** — SIGNATURE CHANGED: fourth argument is now `PriceMaxMon`-shaped, looked up per month the same way. **No longer called by `recomputeChain`** (debt-based re-pricing of `Accrual` is retired — see below) — kept as a standalone public method (own runner, own tests) per the "don't remove public API surface without being asked" rule.
- **`Yamls.recomputeChain(startDate, futureDate, priceMon, payments)`** — SIGNATURE CHANGED: `price`/`priceMax` scalars replaced by a single `priceMon` array; the old fixed-point loop (re-running `applyPriceMaxToDebtMonths` + `computePaymentChain` until `Loaners` stops changing) is GONE — `Accrual` is built once from `priceMon` and chained against real payments a single time. This is a direct consequence of the debt-check removal decided for `buildPriceMonEntries`/`buildPriceMaxMonEntries`: since `PriceMon` no longer varies by debt, there is nothing left for a fixed-point re-pricing pass to converge on. A month needing the `PriceMax` rate instead of `PriceMon` is now a MANUAL edit the user makes to that month's `PriceMon` entry before setting `PriceOK: true` — never automatic.
- **`Yamls.buildPriceDayEntries(priceMon)`** — UNCHANGED shape/signature: `PriceDay[month] = round(priceMon[month] / daysInThatCalendarMonth)`. Still generic over its input array — reused as-is for `PriceMaxDay` by passing `priceMaxMon` instead of `priceMon`. Now reads the (possibly `PriceOK`-frozen) `priceMon`/`priceMaxMon` computed earlier in `#writeChain`, not a freshly-rebuilt one.
- **`Yamls.#writeChain`'s computation order changed**: `PriceMon`/`PriceMaxMon` (with `freezePriceMonEntries`) are now built and written FIRST, immediately after the generic scalar loop — BEFORE `Accrual`/`recomputeChain` runs, since `Accrual` now depends on `PriceMon`. `PriceDay`/`PriceMaxDay` still compute later in the chain (right after `Penalty`), reading the `priceMon`/`priceMaxMon` variables already in scope from the earlier block — no re-fetch, no re-freeze.
- **`Yamls.writePriceMon`/`writePriceMaxMon`/`writePriceDay`/`writePriceMaxDay`** — UNCHANGED: thin `writeYamlArraySection` wrappers, same order-preserving-in-place contract as every other chain writer, same `legacyKeys` migration (`PriceApp`→`PriceMon`, `PriceMaxApp`→`PriceMaxMon`). The `afterKey` fallback anchors (`writePriceMon`→`Penalty`, etc.) are FIRST-INSERT-ONLY, as always — an already-populated real file's own physical layout is untouched regardless of the new in-code write ORDER.
- Regression tests: `tests/Yamls.test.js` → `Yamls.buildPriceMonEntries`/`buildPriceMaxMonEntries` (flat-Price/PriceMax-per-month, no debt input at all) + `Yamls.freezePriceMonEntries` (priceOK-false passthrough, freeze-existing-append-new, ignores-existing's-own-trailing-ALL, empty-existing-falls-back cases) + `Yamls.buildAccrualEntries` (now reads a `priceMon` array, varies per month) + `Yamls.replaceYaml` → the new `"PriceOK: true freezes existing PriceMon/PriceMaxMon months and Accrual uses the frozen rate, not the current Price"` end-to-end fixture (confirms a frozen January month's `Accrual` entry reflects the OLD frozen `PriceMon` rate, never the new `yamlData.Price`, while February — a genuinely new month — is appended at the current rate) + the pre-existing "always writes one Accrual entry per month" fixture (unaffected, `PriceOK` unset/`false`).

### `Yamls.#writeChain`'s generic `replaceTextLine` loop skips array-valued `yamlData` keys — real incident, `Account:` corruption

`#writeChain`'s opening loop (`for (const [key, value] of Object.entries(yamlData)) { this.replaceTextLine(...) }`) now has `if (Array.isArray(value)) continue;` as its first line — mirrors the same array-skip `Excels.generate`'s own generic `{KEY}`-placeholder-clear pass already used (documented above). Before this fix, the loop ran `replaceTextLine` against EVERY key in `yamlData` including array-valued ones, and `replaceTextLine` does `key + ': ' + value` — `String(anArray)` in JS stringifies to `"[object Object],[object Object]"`, a broken YAML scalar `js-yaml` cannot re-parse (`YAMLException: bad indentation of a mapping entry`).

- **Why `Accrual`/`History`/`Payment`/etc. never showed this bug:** each of those keys gets its own dedicated `write*` call LATER in `#writeChain`, which overwrites the generic loop's broken scalar line back into valid YAML before the file is ever read again. A key with NO dedicated writer has nothing to fix it afterward.
- **Real incident:** `NETORA TECHNOLOGY GROUP\ALL 7.contract` carried a hand-placed `Account:` block (no `classes/` code reads or writes this key at all — confirmed via a fleet-wide grep) that predates this rule. A `fillYamlWithInfo` run against it (loading `Account` into `yamlData` via `loadYamlWithDeps`, then hitting the unguarded generic loop) corrupted line 65 to `Account: [object Object],[object Object]`, which then crashed the VERY NEXT read (`Word.contract.mjs`/`Excels.contract.mjs`, both call `fillYamlWithInfo` internally) with a `YAMLException` at `Yamls.loadAndParseYaml`. Fixed by the array-skip guard above; the already-corrupted real file was hand-repaired (`Account:` line restored) as `ALL 8.contract` per the increment-versioning rule below — `ALL 7.contract` itself was left untouched.
- **Scope:** this guard protects ANY array-valued key that might exist in a `.contract` file's `yamlData`, not just `Account` — a future ad-hoc array block hand-added to a real contract (before code support exists for it, same as `PriceMon`/`PriceDay`/`Account` all started) is now left exactly as loaded instead of being corrupted, until/unless a dedicated writer is added for it.
- Regression test: `tests/Yamls.test.js` → `Yamls.replaceYaml` → _"never stomps an array-valued yamlData key (e.g. a stray Account: block with no dedicated writer) into a broken \"[object Object]\" scalar line"_.

### `Yamls.replaceTextLine` now builds every scalar line via real `js-yaml.dump()`, never hand-rolled string concatenation — real incident, `ComNameShort`/`ComNameLong` corruption

`replaceTextLine` used to write `key + ': ' + value` directly (with one narrow special case: a value containing `{`/`}` got wrapped in double quotes) — no escaping for an embedded literal `"` character, no escaping for a YAML-special leading character, nothing matching the rigor `writeYamlArraySection`/`#stripUnnecessaryQuotes` already apply to every ARRAY block. This is the single write path for every SCALAR `yamlData` key (`#writeChain`'s generic loop is its only caller) — including `ComName`/`ComNameShort`/`ComNameLong`, populated straight from a real Didox/MySoliq API response.

- **Real incident:** `NETORA TECHNOLOGY GROUP`'s real `companyInfo.shortName` from the government registry API genuinely contains literal embedded quote marks — `"NETORA TECHNOLOGY GROUP" MCHJ` (the quotes are part of the real legal-name formatting, not a data-entry mistake). Written via the old `key + ': ' + value` concatenation, this produced `ComNameShort: "NETORA TECHNOLOGY GROUP" MCHJ` — a quoted YAML scalar immediately followed by trailing unquoted text, which is a syntax error (`YAMLException: bad indentation of a mapping entry`) — breaking every subsequent `fillYamlWithInfo`/`Word.contract`/`Excels.contract` run against this file until fixed. A first attempt manually stripped the embedded quotes from the real file to unblock parsing; this was WRONG — it silently changed the real company-name data. The correct fix is in the code, not the data: the real value (quotes included) must round-trip through the file correctly.
- **Fix: `Yamls.#dumpScalarLine(key, value)`** — a new private helper `replaceTextLine` now calls instead of hand-rolled concatenation. Builds the line via `yaml.dump({[key]: value}, {lineWidth: -1, schema: yaml.JSON_SCHEMA})` (same `JSON_SCHEMA` every other read/write in this file already uses), then runs the SAME `#stripUnnecessaryQuotes` pass the array writer uses, so a plain safe value still stays unquoted (`ContractDate: 2026-01-19`, not `ContractDate: '2026-01-19'`) — no style change for the common case, only the previously-broken embedded-special-character case is now handled correctly. An empty string is special-cased to bare `key: ` (matching this project's own established blank-field convention — `js-yaml.dump('')` would otherwise produce `key: ''`, a real but stylistically inconsistent departure from every other blank field in a real `.contract` file).
- **The old `{`/`}` → always-double-quote special case is gone, replaced by the generic, more correct behavior**: a value STARTING with `{` (e.g. a literal placeholder-looking string) still gets quoted (now single-quoted, `js-yaml`'s own natural choice — `#isSafeUnquoted` rejects any leading `[-?:,[\]{}]` character), but a value merely CONTAINING `{`/`}` NOT at the very start (e.g. `RC-{N}/2024`) is now correctly left unquoted, since an embedded (non-leading) brace is not YAML-flow-syntax-ambiguous and round-trips fine unquoted — confirmed live.
- Regression tests: `tests/Yamls.test.js` → `Yamls.replaceTextLine` → the embedded-quote-character case (asserts the written line parses back to the EXACT original string, braces included) + the leading-vs-embedded-brace distinction (leading `{` quoted, embedded `{` left unquoted when safe).

### Every literal apostrophe (`'`) in a value is normalized to a backtick (`` ` ``) — GLOBAL, every write AND every read — `Yamls.#normalizeApostrophe`

Fixing the `ComNameShort`/`ComNameLong` quote-escaping bug (above) surfaced a SECOND, independent bug: `Yamls.loadAndParseYaml`'s own hand-rolled line-preprocessing pass (its single-quoted-value branch) re-escaped an embedded apostrophe with a BACKSLASH (`\'`) instead of real YAML's own doubled-single-quote convention (`''`) — a real, validly-written `'MAS''ULIYATI...'` (correct YAML) got mangled into `'MAS\'\'ULIYATI...'` (invalid YAML) the very next time the file was READ, breaking parse all over again on a value that had JUST been correctly written moments earlier.

- **Decision (explicit user instruction): rather than trust every hand-rolled YAML-adjacent string-manipulation pass in this file to escape a raw apostrophe correctly, the apostrophe itself is normalized away at the value level.** `Yamls.#normalizeApostrophe(value)` — `typeof value === 'string' ? value.replaceAll("'", '`') : value` — replaces every literal `'` with `` ` `` (backtick). A single-quoted YAML scalar containing only backticks never needs internal quote-escaping in the first place, so neither the correct doubled-quote convention NOR any hand-rolled re-escaping pass ever gets exercised for this case again.
- **Applied GLOBALLY, at every write AND every read, not just the one field that surfaced the bug:** `Yamls.#dumpScalarLine` (→ `replaceTextLine`), `Yamls.writeScalarSection`, `Yamls.writeYamlArraySection` (normalizes both the key and value of every array entry before dumping), and `Yamls.loadAndParseYaml`'s own post-parse trim step (so a PRE-EXISTING file written before this fix existed, or any file this session hasn't touched, still gets normalized on its very next read — the fix self-heals old data, not just new writes).
- **Real incident, exact sequence:** `NETORA TECHNOLOGY GROUP\ALL.contract`'s real `ComNameLong` (`"NETORA TECHNOLOGY GROUP" MAS'ULIYATI CHEKLANGAN JAMIYAT` — a genuine legal company name containing both an embedded double-quote pair AND an embedded apostrophe) broke parse twice in a row: first from the double-quote bug (fixed by `#dumpScalarLine`'s real `js-yaml.dump()`), then immediately again from THIS apostrophe bug, confirmed live via the exact same user-run script (`scripts/Yamls/contractFill.mjs`) failing with `YAMLException: bad indentation of a mapping entry` at the `MAS''ULIYATI` line. Fixed in two places: the real file's `ComNameLong` value itself (`'` → `` ` ``, per explicit user instruction — the apostrophe in real company-name data is intentionally replaced, not preserved), and `loadAndParseYaml`'s own single-quote re-escaping branch corrected to use YAML's real `''` doubled-quote convention instead of backslash (defense in depth, for any future value this normalization hasn't yet reached).
- **A full sweep of every remaining `'` in the real file confirmed no other un-normalized apostrophe exists** — every other `'` occurrence is a legitimate YAML outer-quote delimiter (wrapping a negative number like `'-1,600,000'`, or `'Yes'`/`'No'`), never an embedded apostrophe inside content.
- Regression tests: `tests/Yamls.test.js` → `Yamls.replaceTextLine`/`Yamls.writeScalarSection`/`Yamls.writeAccrual` (each asserts an embedded `'` in the value comes out as `` ` `` in the written file) + `Yamls.loadAndParseYaml` (asserts a raw un-normalized apostrophe AND a pre-existing valid doubled-quote value both normalize to `` ` `` on read).

### Rental reconciliation (ActReco) — monthly penalty/debt calculation rule

`Excels.generate` builds a per-tenant rental reconciliation act from real evidence folders (`Bank-OT`, `Card-OT`, `EHF-IN`, `BaaR-OT`, etc., named per `Excel.CellNames` in `config.yml`, each a sibling of the tenant's own `.yml` under `folderALL`). When manually verifying or recomputing a reconciliation act's debt/penalty figures (as opposed to trusting the workbook's own `SUM`-based formulas blindly), the correct calculation rule is:

- **Monthly periods are anchored to the rental start date (`RENT_START`), never to when a payment happens to arrive.** Period _N_ runs from `RENT_START + (N-1) months` to `RENT_START + N months`; its due date is the end of that window (same day-of-month as `RENT_START`, one month later).
- **Each real payment covers a chain of consecutive whole months, starting right where the previous payment's coverage left off** — `floor(amount / monthlyRate)` months, chained onto `coveredUpToIdx + 1`. A payment never retroactively re-covers an earlier already-covered month, and it never "banks" leftover credit into the indefinite future beyond the whole months it actually buys.
- **A period fully inside some payment's coverage chain is PAID — zero qarz (debt), zero penya (penalty) — regardless of which calendar date the covering payment itself arrived on.** (Real incident: an earlier cumulative-sum model wrongly used the _payment's arrival date_ vs. each period's own due date to decide "OK", which produced a coincidentally-correct total but the wrong reasoning — corrected to the chained-coverage model above per direct user correction in this project's history.)
- **A period NOT covered by any payment's chain is unpaid from its own due date.** `Сумма задолженности` (qarzdorlik, the `Loaners` block) still accrues at the monthly rate for that period via this chain — **but `пеня` (penalty) itself no longer derives from this chain at all; see the daily-balance model below**, which supersedes the older "accrue daily from due date, cap at 50% of that period's rent" reading of §21.2/§21.3.
- **Never assume a single large prepayment recurs as a pattern for future months** — a tenant paying 6 months at once in the past does not imply every future gap will also self-resolve; each period's coverage is derived strictly from the actual payment chain that exists on disk, never extrapolated.
- **A partial-month period's accrual is prorated by real day count, then rounded to the nearest WHOLE SO'M ONLY — never a raw fractional-tiyin figure, and never rounded up to the nearest 1,000.** Formula: `round((daysInPeriod / daysInThatCalendarMonth) * monthlyRate)`. E.g. a period from day 9 to the end of a 31-day month is 23 days: `23/31 × 390,000 = 289,354.84` → rounds to **289,355** (never `289,354.84`, but also never bumped up to `290,000` — a full-month `Accrual` entry stays whatever whole figure `Price`/`PriceMax` already is, a partial-period entry is never forced to match that same round-thousand shape).
- **Penalty is a prepaid RUNNING-BALANCE model (contract §21.1 + §3.7/§1.20), not a %-of-Accrual model — like a provider account: money credits the balance, rent debits it daily, and every calendar day the balance is negative (beyond the ONE-TIME `PeriodStart` grace day) costs a fixed daily fee, capped per month.** Concretely: `Account` (the written `.contract` block — see its own dedicated section above) simulates day by day from `PeriodStart` through `PeriodEnd`, debiting `PriceDay` (the prepay discount) when the previous day's balance was `>= 0` or `PriceMaxDay` (the full rate) when it was already negative, then adding that day's own `History` entry (payment positive, return already negative). **`Yamls.computePenaltyDays` grants the 1-calendar-day grace period from §3.7/§1.20 EXACTLY ONCE — to `Account`'s own first entry (`PeriodStart`'s day) — never re-granted for any later deficit streak.** Every other negative-balance day counts toward `PenaltyDays`, including the first day of a streak that starts fresh after the balance had recovered to `>= 0` (confirmed via a real user correction against real `Account` data: 14 consecutive negative days must produce `PenaltyDays: 14`, not 13 — the earlier "fresh grace day per streak" model was wrong). `Yamls.computePenalty` then multiplies: `Penalty[month] = PenaltyDays[month] * config.yml's Penalty.PerDay` (default `50,000`), **capped at HALF that month's own `PriceMaxMon` amount** — the old "50% of that period's Accrual, immediately, no cap" model, the "daily from due date, capped at 50%" model, and the brief "no cap at all" model are ALL retired in favor of this one.
- **`Payment:` and `Returns:` in a tenant `.yml` are FLAT, date-keyed arrays — NOT `"start#end": amount` per-Accrual-period arrays.** Each is a merge of its underlying `-OT`/`-IN` scan-folder arrays (`Yamls.mergeDateKeyedArrays`) — same-date entries from different sources summed together (e.g. a `Bank-OT` and a `Card-OT` payment landing the same day become one `Payment:` entry, their amounts added) — shape `[{ '2026-04-21': '1,600,000' }, ...]`, sorted by date, plus a trailing `{ ALL: sum }` appended at write time (`Yamls.appendAllTotal`). `Payment` = `Bank-OT + Card-OT + BaaR-OT + Trans-OT`; `Returns` = `Bank-IN + Card-IN + BaaR-IN` (`Trans-IN` deliberately excluded — no dedicated scan-folder/`Excel.CellNames` key for it in this project). **The old invariant `Payment[i] + Loaners[i] === Accrual[i]` (true when `Payment` was a chain-allocated per-period array) NO LONGER HOLDS** — `Loaners` is still chain-allocated internally (via `Yamls.recomputeChain`/`computePaymentChain`, now summing `Bank-OT+Trans-OT+Card-OT+BaaR-OT` — `BaaR-OT` was added to this internal chain too), but the WRITTEN `Payment:` key is the separate flat-merge view described above; the two are intentionally decoupled.
- **Field ordering in a tenant `.yml` is now WHATEVER THE REAL FILE ALREADY HAS — `writeYamlArraySection` updates an existing key strictly in place (see [Editing an Existing YAML/JSON File](#requests) in global `CLAUDE.md`), never relocates it.** The `afterKey` chain each `write*` wrapper passes (`writeAccrual`→`ComBase`, `writePayment`→`Accrual`, `writeFaktura`→`Payment`, `writeFakturaSend`→`Faktura`, `writeLoaners`→`Faktura`, `writePenaltyDays`→`Loaners`, `writePenalty`→`PenaltyDays`, `writeReturns`→`Penalty`; `writeCellArrays`'s own `Excel.CellNames` chain starts at `'Returns'`) is ONLY the fallback insertion order used the very first time a key is EVER written into a file that has never had it before — a fresh `.contract` (from `smarts-firm-docums`'s bundled template) gets `ActDateEnd` → `ContractDateEnd` → `ComBase` → `Accrual` → `Payment` → `Faktura` → `FakturaSend` → `Loaners` → `PenaltyDays` → `Penalty` → `Returns` → every `Excel.CellNames` key this way, but an already-populated real file's own order/grouping/comments (e.g. `Accrual`+`Loaners` grouped, `Payment`+its own `-OT` sources, `Returns`+its own `-IN` sources, `Faktura`+`EHF-IN`, `PenaltyDays`+`Penalty`, each separated by a `#####`-style comment) is preserved exactly, forever, once it exists. Exactly one blank line is added before/after a genuinely NEW block on its first insert; an existing block's own surrounding spacing/comments are never touched.
- **`Accrual` reads each month's own rate from `PriceMon` — there is no automatic `Loaners`/debt-based switch to `PriceMax` for `Accrual` anymore (retired — see the `PriceMon`/`PriceMaxMon` architecture-reversal section above).** A month that needs the `PriceMax` rate instead of `PriceMon`'s current value is a MANUAL edit the user makes to that specific month's `PriceMon` entry, then locks in via `PriceOK: true` (see below) so it survives future fills. The whole chain is still re-run end to end on every `replaceYaml` (`recomputeChain` then `computePenaltyDays`/`computePenalty`), never patched in place — only the debt-triggered auto-switch itself is gone.
- **`PriceMon`/`PriceDay` report the tariff's own flat monthly/daily rate per calendar month — the PERMANENT SOURCE OF TRUTH every other calculation reads from (see the dedicated architecture section above), not a downstream display figure anymore.** `PriceMon[month]` is built directly from `Price` (or, under `PriceOK: true`, a frozen on-disk value the user hand-set — see below), never prorated, never debt-conditioned. `PriceDay[month]` = `PriceMon[month]` divided by that month's own real day count, rounded to the nearest whole so'm — the effective daily rent rate for that month, and the rate `Account` itself debits daily. See [`PriceMon`/`PriceMaxMon`](#requests) above for the implementing code and the `PriceOK` freeze mechanism.
- **`Account` is the client's own daily running balance — a provider-account-style ledger, one entry per calendar day, distinct from `PriceMon`/`PriceDay`'s monthly source-of-truth figures.** Day 1 (`PeriodStart`) is `History`'s own entry for that date, or `0` (a client normally hasn't paid yet on day 1, so it debits nothing). Every day after that debits that day's own month's `PriceDay` rate off the previous day's balance, then adds that day's own `History` entry (a payment is a positive `History` amount, a return is already negative — both apply as a plain add, never a separate credit/debit split). See [`Account`](#requests) above for the implementing code.
- **The whole `PriceMon`→`PriceMaxMon`→`Accrual`→`Payment`→`Faktura`→`FakturaSend`→`Loaners`→`PenaltyDays`→`Penalty`→`Returns` chain is code-driven, never hand-edited as the source of truth** (the one exception: `PriceMon`/`PriceMaxMon`'s own historical months, once frozen via `PriceOK: true`, ARE meant to be hand-edited — that is the entire point of the freeze). `Yamls.freezePriceMonEntries` (the `PriceOK` freeze), `Yamls.recomputeChain` (which calls `buildAccrualEntries` → `computePaymentChain`, reading `PriceMon` for each month's rate, no fixed-point loop anymore), `Yamls.mergeDateKeyedArrays` (the flat `Payment`/`Returns` merge), `Yamls.computeFaktura`/`computeFakturaSend`, and `Yamls.computeDailyBalance`/`computePenaltyDays`/`computePenalty` (the daily-balance penalty model) are the single authoritative implementation — `Yamls.fillYamlWithInfo` calls them and writes the blocks via `writePriceMon`/`writePriceMaxMon`/`writeAccrual`/`writePayment`/`writeFaktura`/`writeFakturaSend`/`writeLoaners`/`writePenaltyDays`/`writePenalty`/`writeReturns`.
